# Zigbee manifest baud rates

Each selected radio image can declare its application UART rate as an integer:

```json
{
  "variants": {
    "MGM24": {
      "fw_url": "https://example.com/radio.gbl",
      "baudrate": 460800
    }
  },
  "version": "9.1.2.1"
}
```

The same field works in a flat manifest. A root-level `baudrate` is a default
when the selected variant omits it; a variant's field takes precedence. Metadata
from an unselected variant is never used. Missing metadata retains the current
rate, including direct custom GBL URLs, which have no manifest metadata.

The updater validates metadata before erasing or programming. The value must be a
JSON integer from 9600 through 921600, and, when a saved baud selector is bound,
one of its configured options. Strings, nulls, fractional numbers and unsupported
rates fail the check without changing the UART or saved settings.

After a successful transfer, the target resets and the gateway applies the new
application baud to the UART hardware. It updates the existing baud selector,
when present, and synchronously saves a numeric preference before the serial
bridge can resume. The selector's normal baud-change script is suppressed during
this update so it cannot resume the bridge early. Subsequent reboots restore the
numeric rate before any startup radio probe. Existing saved selector values seed
the preference on migration; numeric preferences survive selector reordering.

Checks alone never apply or save a rate. A failed transfer restores the previous
rate. If persistence itself fails after programming, the UART stays at the new
rate required by the installed image and the update reports an error. The logs
identify that saving failed; a reboot may still restore the old saved value.

Bootloader rates are independent of this field. EFR32 uses 115200 for its
bootloader. CC2652 keeps its configured bootloader/autobaud rate, currently 500000
in these profiles. Its application UART now explicitly reloads hardware settings
when switching between bootloader and application rates.

## Prepared feeds

Changes in the local `tube_gateways` checkout preserve its existing versions,
image URLs and user changes:

| Feed | Application baud |
| --- | ---: |
| `docs/firmware/efr32manifest.json`: stable 7.4.4, MGM24 and BM24 | 115200 |
| `docs/firmware/efr32manifest_beta.json`: beta 9.1.2.1, MGM24 and BM24 | 460800 |
| Existing CC2652 feeds, including active `misc/manifest.json` | 115200 |
| New `docs/firmware/efr32manifest_mgm12.json`: archived MGM12 Pro1 7.4.3 | 115200 |
| New `docs/firmware/efr32manifest_mgm210.json`: archived original MGM210 Series 2 7.4.3 | 115200 |

The legacy feeds reference their own archived images. The four standalone older
profiles now use native flashing with software-flow UARTs; see
`older-efr32-flashing.md`. They do not use MG24 images. MGM210 PoE 2022/2023 use
the separate `efr32manifest_mgm210_poe.json` feed and its 2022 radio image.
New gateway OTA feeds for these profiles are generated by the normal release
workflow. Local feed edits and new radio feeds must be published separately to
be reachable by deployed devices; no release was published by this change.

## Component source

The patched `cc2652_flasher` and `efr32_flasher` components are bundled locally,
alongside the shared `zigbee_firmware_baud` helper, for reproducible builds.
Their baseline is `tube0013/esphome-components` commit
`0e35b4afe1ad12b17418626d3bd75b7bcad52de6`. Existing licenses are retained.
Upstream stream-server and identity-reader dependencies remain separate. The
user's separate `esphome-components` checkout and its uncommitted work are not
modified.

Tests cover JSON types and selected-image precedence, preference restore and
selector migration, persistence errors, actual firmware builds, and frontend baud
refresh while retaining unsaved user choices on ordinary status polls.
